# Castle5000 Retrieval

Text -> image retrieval web app for ~40 students, backed by CLIP + FAISS,
submitting results to [DRES](https://github.com/dres-dev/DRES). Implements
an internal technical note covering the system design (not included in
this repo).

Students type a text query, get back a grid of matching images (CLIP
embeddings + FAISS nearest-neighbor search), and submit the one they think
is correct straight to DRES for scoring.

## Repo layout

```
backend/app/        FastAPI app (main.py, search.py, dres_client.py, ...)
backend/tests/       Unit tests (no network, no real DRES, no GPU needed)
backend/Dockerfile
frontend/            Static single-page UI (no build step)
tools/build_index.py Offline: images -> embeddings -> FAISS index + thumbs
tools/check_ids.py   Compares ids.json against a live DRES media collection
tools/mock_dres.py   Fake DRES server for testing (200/202/401/404/412)
tools/loadtest.js    k6 script: 40-50 concurrent login+search+submit
data/                Generated by build_index.py; never commit images/index
```

## 1. Setup

```bash
python3.11 -m venv .venv   # 3.11, not 3.14 -- see "Known issues" below
source .venv/bin/activate
pip install -r requirements.txt
```

## 2. Build the search index (offline, once)

```bash
python tools/build_index.py --images-dir /path/to/Castle_5000 --out-dir data
```

Produces `data/index.faiss`, `data/ids.json`, `data/thumbs/`,
`data/embeddings.npy`, `data/build_stats.json`.

For local dev, symlink the real image corpus into `data/images` instead of
copying 1GB+ of files into the repo:

```bash
ln -s /path/to/Castle_5000 data/images
```

(In a real deployment this is a real read-only bind mount instead -- see
`docker-compose.yml`.)

## 3. Configure

Copy the example env file and fill it in:

```bash
cp .env.example .env
```

`backend/app/config.py` loads `.env` automatically (`pydantic-settings`,
`env_file=".env"`) -- no need to export anything by hand or pass env vars
inline on the uvicorn command line.

| Env var | Meaning |
|---|---|
| `DRES_BASE_URL` | Base URL of the DRES server, e.g. `http://localhost:8090` (local mock), `http://localhost:8088` (a real local DRES instance), or `http://dres:8080` inside the compose network |
| `DRES_EVALUATION_ID` | The ID of the running evaluation/run in DRES. Without it, `/api/task` and `/api/submit` just report "no evaluation configured" instead of erroring. Find it in the DRES admin UI for the evaluation you're running. |
| `SESSION_SECRET` | Random secret for signing this app's own session cookie (not sent to DRES). Must be set to a real random value in production. |
| `SESSION_COOKIE_SECURE` | `true` in production (HTTPS); `false` only for local `http://` testing. |

`.env` is gitignored -- never commit real secrets or credentials. See
`.env.example` for the full list of settings (rate limits, timeouts, etc.)
and their defaults.

## 4. Run it

### Option A: local dev, no real DRES (fastest way to see it working)

Spins up a fake DRES server alongside the app, so you can try the whole
flow (login -> search -> submit) without any real DRES instance. The
defaults in `.env.example` already point at this mock server, so this
works as-is after `cp .env.example .env`:

```bash
source .venv/bin/activate
uvicorn tools.mock_dres:app --port 8090 &                       # fake DRES
uvicorn backend.app.main:app --app-dir . --port 8000 &
open http://127.0.0.1:8000/          # login: student / student
```

- Local dev uses port **8000**, not 5000: on macOS, AirPlay Receiver
  listens on port 5000 and answers browser requests with a `403 Access
  denied`, even on `127.0.0.1`. (Docker still uses 5000 internally.)

### Option B: against a real DRES instance

Point the app at a real, already-running DRES server instead of the mock.
Edit `.env` -- say DRES is running locally on port `8088`:

```bash
DRES_BASE_URL=http://localhost:8088
DRES_EVALUATION_ID=<evaluation-id-from-DRES-admin-UI>
SESSION_SECRET=dev-secret
SESSION_COOKIE_SECURE=false
```

Then run the app the same way as Option A (no mock DRES needed this time):

```bash
source .venv/bin/activate
uvicorn backend.app.main:app --app-dir . --port 8000 &
open http://127.0.0.1:8000/          # login with a real DRES account
```

**How submission actually works:** students never talk to DRES directly.
Clicking "Submit" in the UI sends `POST /api/submit {"id": "<image_id>"}` to
*this app*, which looks up the student's DRES session and forwards it as
`POST /api/v2/submit/{evaluationId}` to DRES
(`backend/app/dres_client.py`'s `submit()`). That's deliberate: it lets the
app rate-limit submissions, validate the image ID exists, and handle an
expired DRES session without ever caching the student's password.

To submit a result from the command line (e.g. for testing, without
clicking through the UI), log in first to get a session cookie, then call
`/api/submit` with that cookie:

```bash
# 1. Log in (through this app, not DRES directly) and save the session cookie
curl -s -c cookies.txt -X POST http://127.0.0.1:8000/api/login \
  -H "Content-Type: application/json" \
  -d '{"username": "student", "password": "student"}'

# 2. Submit an image ID using that cookie
curl -s -b cookies.txt -X POST http://127.0.0.1:8000/api/submit \
  -H "Content-Type: application/json" \
  -d '{"id": "08_1002.jpg"}'
```

To sanity-check the DRES connection itself, independent of this app, call
DRES's own API directly:

```bash
# Log in directly against DRES -> returns a sessionId
curl -s -X POST http://localhost:8088/api/v2/login \
  -H "Content-Type: application/json" \
  -d '{"username": "student", "password": "student"}'
# -> {"id": "...", "username": "student", "sessionId": "<session-id>", ...}

# Submit directly against DRES using that sessionId
curl -s -X POST "http://localhost:8088/api/v2/submit/<evaluation-id>?session=<session-id>" \
  -H "Content-Type: application/json" \
  -d '{"answerSets": [{"answers": [{"mediaItemName": "08_1002.jpg"}]}]}'
```

**Before go-live**, confirm DRES actually created media items under the
exact filenames in `data/ids.json`:

```bash
python tools/check_ids.py \
  --dres-base-url http://localhost:8088 \
  --username admin --password admin \
  --collection-name Castle5000 \
  --ids-path data/ids.json
```

## Docker

```bash
docker compose build
docker compose up -d
```

`docker-compose.yml` is just the `retrieval` service, meant to merge into
the shared compose file with `dres` and `caddy` (per the note). It never
publishes a host port; only `expose`s 5000 for Caddy inside the same
compose network. It reads `DRES_BASE_URL`, `DRES_EVALUATION_ID`,
`SESSION_SECRET`, etc. the same way `docker compose` always does -- from
a `.env` file in the project root -- so the same file from step 3 works
here too (`SESSION_SECRET` has no default and is required).

## Known issues

- **macOS: faiss + torch in the same process crashes** (`OMP: Error #15`,
  then a segfault once real work runs on both). Both bundle their own
  OpenMP runtime. Fixed in `backend/app/search.py` and
  `tools/build_index.py` by forcing single-threaded OpenMP
  (`KMP_DUPLICATE_LIB_OK=TRUE`, `OMP_NUM_THREADS=1`,
  `faiss.omp_set_num_threads(1)`, `torch.set_num_threads(1)`) before
  either library does real work. This costs nothing here: the backend only
  ever encodes one short query string per request, and the offline index
  build still uses the GPU (MPS) for the expensive part (image encoding);
  only FAISS's own tiny flat-index operations are forced single-threaded.
- **Python 3.14 (the system default here) has no working `faiss`/`torch`
  wheels yet** -- the venv was built with Homebrew's `python3.11` instead.
- `check_ids.py` and the real DRES integration test (note section 9) have
  not been run against the actually-deployed DRES+evaluation yet; they
  need real admin credentials and a created media collection first.

## DRES integration: verified against the real spec

`backend/app/dres_client.py` and `tools/mock_dres.py` were written against
the actual public DRES v2 OpenAPI spec
(`github.com/dres-dev/DRES`, `doc/oas.json`, checked 2026-10-06), not
guessed -- endpoint paths, `LoginRequest`/`ApiUser`/`ApiClientSubmission`/
`ApiClientAnswer`/`SuccessfulSubmissionsStatus`/`ApiClientTaskTemplateInfo`
field names all come from that file. Two gaps found that need checking
against the actual deployed DRES instance before go-live:

1. `ApiClientTaskTemplateInfo` (the `/api/v2/client/evaluation/currentTask`
   response) has no task-start timestamp, only a `duration`. The frontend
   therefore shows an *approximate* countdown (`~m:ss`) measured from when
   it first observed the task, not DRES's authoritative clock. If the
   deployed DRES exposes a start time somewhere else, wire it in instead.
2. The spec's own security annotations are empty (`"security": []`) on
   every endpoint even though 401s clearly happen in practice (confirmed
   against the locally running DRES at `localhost:8080`, which returns 401
   on `/api/v2/evaluation/info/list` without a session) -- the spec's
   `security` field just isn't populated, not a real absence of auth.

## Decisions made on the note's open questions (section 11)

These were genuinely open in the note; here's what this implementation
assumes, so they can be corrected before go-live if wrong:

- **Codebase**: none existed; built from scratch per the note's suggested
  stack (FastAPI backend, plain static frontend, one container).
- **Query modality**: text only (CLIP text encoder), per the note's own
  assumption.
- **Embedding model**: `open_clip` `ViT-B-32` / `laion2b_s34b_b79k`, CPU- and
  Apple-Silicon-MPS-friendly, 512-dim. Swappable via `EMBED_MODEL_NAME` /
  `EMBED_PRETRAINED`, but the backend and `tools/build_index.py` must agree
  (changing it requires rebuilding the index).
- **Image IDs**: the filename, including extension, exactly as it appears
  in the source image directory (e.g. `08_1002.jpg`). All 5000 filenames
  in the real corpus are already unique and stable, so no renaming was
  needed. This value is sent verbatim as `mediaItemName` to DRES --
  **run `tools/check_ids.py` against the real DRES media collection before
  go-live** to confirm DRES created items under these exact names.
- **DRES session on 401 during submit**: the note says both "retry login
  once" and "never retry POST submit, and never cache the password." Since
  the password is never cached (per the note's own security requirement),
  this implementation resolves the tension by invalidating the local
  session and asking the student to log in again, rather than silently
  re-authenticating -- see `backend/app/main.py`'s `submit`/`get_task`
  handlers and the comment in `dres_client.py`'s `DresAuthError`.
- **Image/thumb auth**: chose "require login" (not Referer-based) for
  `/images/{id}` and `/thumbs/{id}` -- simpler and matches the rest of the
  API.

Still open, deliberately not decided here (need your input / the real
VPS): per-student vs per-group accounts, the exact scoring/penalty rules
(only affects the confirm-dialog copy), and the final latency threshold
(section 9's "ngưỡng cần chốt").
